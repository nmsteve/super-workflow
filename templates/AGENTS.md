# Active Working Rules

- Gate on go-ahead / answer-only: when asked a question, answer only. Do not write code, edit files, create issues, create branches, commit, or implement anything until explicitly told to proceed.
- Ask in plain text: when you need to ask a question or request confirmation, put it in your plain-text reply; do not use a question-screen / multiple-choice picker UI. For a single selectable question, omit the question number and label choices with sequential lowercase letters (`a`, `b`, `c`, etc.). For multiple selectable questions, number the questions sequentially (`1`, `2`, etc.) and use lowercase lettered choices beneath each one. Do not add a redundant reply-format instruction when the expected response is already clear from the question and choices.
- Numbered-answer replies: when asking multiple questions, expect my answers in one line separated by commas, keyed in order to the question numbers - e.g. `a, b, a`. Any segment may be my own free-text answer instead of a letter, used when none of the choices make sense to me; treat it as a custom answer for that question. Parse each segment against its question number and do not ask again for answers already given in that form. Answers map in order: a single answer such as `a` is for question 1, two answers are for questions 1 and 2, and so on. If I answer fewer questions than were asked, apply those answers and ask again only about the unanswered ones; if there are more segments than questions (e.g. a free-text answer contains a comma), ask once to clarify.
- Wide table layout: when creating a table, favour few columns with long rows so the table fits the screen width well; avoid many narrow columns that wrap or squeeze text.
- Plan before issue prompts: when asked to work on something, plan first and present the plan; ask about creating an issue only at the end, after the plan — not upfront.
- Parallelise independent work: Run independent steps together, not one after another: before starting a task, identify the steps that do not depend on each other and run them in parallel (several tool calls in one message, or background agents) instead of sequentially. Keep steps that need an earlier step's result in order.
- Hard rule — background agents for all work: run every piece of task work (investigation, file edits, builds, test runs, remote/server operations, syncs) in a background agent, where the tool supports background agents, so the main conversation stays free. The only exception is trivial one-shot reads, such as a single `grep` or `cat`, which may run inline. The main conversation only plans, asks, relays agent results, and summarizes. Relay each agent's result when it completes, and never predict or fabricate results that have not arrived.
- Summarize before and after: before starting a task, summarize the understanding and wait for confirmation. After finishing, summarize what changed and include changed-file references where applicable. Use a bare `path:line` reference relative to the opened workspace root — not Markdown link syntax `[text](path)` and not an absolute path, because both are not ctrl-clickable in the terminal. Put each changed-file reference on its own line, followed by a short description.
- Brief task summaries: report finished work in three sections — `Results` (what happened, plus the changed-file links), `Considerations` (open choices), `Action needed` (concrete next steps and blockers). Write each section heading as a markdown level-2 heading (`## Results`, `## Considerations`, `## Action needed`) so it renders large and bold. Do not number the section headings themselves. All three sections use the same structure: sequential numbered points (`1.`, `2.`, `3.`) with a blank line before every point. Lettered options (`a.`, `b.`) belong to Considerations and nowhere else, with one marked *(recommended)*. Anything that presents a choice goes under Considerations — including a step that needs the user's go-ahead before you act, which is a decision for them and belongs there, not in Action needed. Action needed carries only concrete next steps and blockers with no choice attached, so it never has lettered options; Results never has them either, since it reports what happened. In Results, each changed-file link is its own numbered point at the same level as the narrative points, on its own straight line. Never nest a plain, unlettered line beneath a numbered point: the terminal renderer turns it into a new list item and collapses the spacing around the surrounding points. Lettered options are the only thing that may sit beneath a numbered point. Spacing is required, not optional, and is the single most-missed part of this rule: put a blank line above each section heading, a blank line between each lettered option, and a blank line before every numbered point. The blank line before a numbered point is mandatory even when the line above it is the last lettered option of the previous point — that is exactly the place it gets dropped. No numbered point may ever sit on the line directly after an option, so `1.`, `2.`, `3.` never run together. Follow this literal shape:

      ## Results

      1. <what happened>

      2. [file.ts](/abs/path/file.ts:12) - <short description>

      3. [other.ts](/abs/path/other.ts:40) - <short description>

      4. <what happened>

      ## Considerations

      1. <first decision>

         a. <option> *(recommended)*

         b. <option>

      2. <second decision>

         a. <option> *(recommended)*

         b. <option>

      ## Action needed

      1. <next step or blocker>

      2. <next step or blocker>
 Terse throughout; no preamble or restatement. Use `None.` for an empty section. Only raise a Consideration where a real decision is open — do not manufacture choices.
- Design confirmation gate: for design work, first create a sketch or wireframe when practical, present it to the user, and receive explicit confirmation before implementing the final design.
- Ask before creating Claude Docs: never create a document with the Claude Docs connector (or any claude.ai doc/artifact the user did not explicitly ask for) without first asking and getting explicit approval. When content would suit a document, offer it in one line and wait; otherwise answer in chat.
- Slack messages as drafts: when asked to message someone on Slack, never send it with `slack_send_message` — messages sent that way show "Sent using Claude". Create a Slack draft instead (`slack_send_message_draft`) in the right DM or channel, report the draft link, and let the user review and send it themselves. This applies even when the user says "send".
- Setup docs confirmation: before giving setup, install, authentication, configuration, or similar environment instructions, confirm current commands and behavior from official documentation or another reliable primary source, then state what was confirmed and from where.
- Production Docker environment validation: before rebuilding or recreating a production Docker Compose service, identify the canonical production deployment environment and compare it with the proposed build environment. Reject production-facing URLs, hosts, API endpoints, and Socket/WebSocket endpoints that contain `localhost`, loopback addresses, development domains, or blank required values. When frontend tools may inline environment variables at build time, inspect the generated production bundle and test the affected public endpoints before reporting deployment success. Do not build production from a development checkout's `.env` unless its production values have been explicitly validated.
- Instruction sync automation: scripts must read operational values from `.env`/`.env.example` rather than hardcoding private hosts, paths, repos, account identifiers, or credentials.
- Public workflow publishing: public copies must be reusable workflow templates, not private operational dumps. Remove private server names, SSH topology, account identifiers, internal repo/project names, credentials, private paths, and non-public operational details. Replace them with clear placeholders or configurable examples.
- Public workflow publishing after rule updates: after every global/working instruction rule update, also update and push the configured public workflow repository when the change is reusable and public-safe, even if the public wording needs later refinement, so changes are retained remotely. If the rule contains private operational details or is not appropriate for public reuse, do not publish it publicly and state why.
- New task issue gate: when asked to implement a new feature, fix, or chore without an issue number, first analyze the request and current repo context, check the current branch name, and infer whether the branch already matches the requested task. If the current branch appears to match the task, continue in that task context and do not repeatedly ask to create a new issue for every prompt. If the current branch does not match the task, summarize the proposed work and ask whether to create an issue before implementation. For investigation-only tasks, do not ask to create an issue or branch; investigate read-only and report findings. If implementation is requested only after the investigation, ask about issue/branch creation at that point.
- Issue creation on request: when the user explicitly says to create an issue (e.g. 'create an issue') after the work has been discussed, create it directly from that discussion without sharing a draft for approval, then report the created issue's title, number and link. Share a draft first only when proposing an issue the user has not explicitly asked for.
- Issue tracker defaults: when creating tracker issues, set the status to the configured initial status such as `To Do`, assign the current cycle or iteration when applicable, and use configured domain-specific assignees for special categories such as mobile issues.
- Related issue naming: for related issues covering the same item across target sites/repos such as frontend, backend, or mobile, use the same shared description/follow-up description for each issue, such as `wallet withdrawal validation`; do not add layer words such as `frontend`, `backend`, or `mobile` when the target-site/repo identifier already identifies the layer.
- Broad issue scope, fix during testing: prefer fewer, broader-scoped issues over many narrow follow-up issues. While testing an issue's work, fix anything found broken or missing directly under the current issue instead of stopping to file a separate follow-up. Only create a separate issue when the problem is clearly outside the current issue's area.
- Issue status tracking: when the work branch for an issue is created and published, set the issue to **In Progress**; after its PR merges, set it to **Done**. In Linear, change the issue's status; on GitHub, move the issue's Projects board card if it has one (`Closes #N` closes the issue itself at merge). Do this without asking.
- Linear issue limit — archive via API token: the Linear MCP server cannot archive issues. When creating a Linear issue fails because the workspace issue limit is reached, archive the oldest Done/Cancelled issues through the Linear GraphQL API with that workspace's API token (not MCP), without asking, only as many as needed, then create the new issue through MCP as usual. Never archive an open issue. Report the archived identifiers. If no token can be found locally, report the blocker.
- Branch discipline: when an issue number is provided or created, create a feature branch before file edits: for a GitHub issue, name it `{issue-number}-{short-description}`; for a Linear issue, use the issue's `gitBranchName` exactly (lowercase `<team-key>-<issue-number>-<slug>`, e.g. `eng-123-web-app-compact-picker`), with no layer or other prefix added — the target site at the start of the issue title already carries the layer into Linear's slug. Do not edit protected long-lived branches directly unless explicitly instructed.
- Session rename automation: after creating and publishing an issue branch, run `codex-rename-session <exact-branch-name>` as a normal implementation step and continue without pausing for user confirmation. Do not display or ask the user to run `/rename`. If the helper is unavailable or fails, report the concrete error and continue without blocking implementation; do not change the established branch naming convention.
- DeepSeekQ session handoff: when I say 'handoff a session to DeepSeekQ', treat it as a manual handoff: (1) locate the specified session and read it; (2) review its full context, progress, decisions and outstanding tasks; (3) identify exactly where the previous session stopped; (4) transfer the relevant context to DeepSeekQ; (5) resume work from that point without repeating completed tasks. This manual process is required because DeepSeekQ's normal session-resume functionality is not configured to resume cloud sessions.
- Branch creation merge check: before asking the user to confirm creating a new branch or creating it, check the current branch and whether it has been merged into the configured integration branch such as `develop`, falling back to `main` when no integration branch exists. If the current branch is the base branch, treat it as ready for new branch creation. If the current branch is not the base branch and is unmerged, report the current branch and merge status, then ask how to proceed before creating or switching branches.
- Dependent feature branch workflow:
  1. Fetch the latest upstream base before creating or updating a feature branch.
  2. Determine whether the new work depends on another feature branch.
  3. If there is no unmerged dependency, create the branch from the latest upstream base.
  4. If the dependency is unmerged, create the branch from that dependency branch.
  5. Before opening or updating a PR, check whether the dependency has merged and whether upstream has advanced.
  6. If the dependency has merged or upstream has advanced, rebase the appropriate branch onto the latest upstream base.
  7. Update stacked branches from oldest to newest.
  8. Verify that each PR contains only its intended changes before marking it ready or merging it.
- Script branch exception: when changing a designated project helper script such as `/dev.sh`, use the current branch by default. If the current branch is a protected base branch such as `develop`, `main`, or `master`, do not edit there directly; create or use an appropriate work branch first.
- Branch and publish before work: when creating an issue/work branch, first fetch the remote that holds the configured base branch so the base is current, then create the branch in a new worktree with `git worktree add -b <branch-name> ../<branch-name> <remote>/<base>` run from inside the main checkout. Inside the worktree, immediately publish it with `git push -u origin <branch-name>` before making file edits, and verify with `git branch -vv` that it tracks `origin/<branch-name>`, not the base branch.
- WIP check before branching: before creating a worktree, run `git status --porcelain` in the main checkout and report any uncommitted WIP there. Leave it untouched; worktrees are created from the fetched remote base, so WIP never blocks them.
- Worktrees by default: do all task work in a linked git worktree, without asking for approval. Each repo is a folder in the workspace with every checkout inside it named by branch: the main checkout at `<workspace>/<repo>/<base-branch>/` (e.g. `my-app/main/`) and each worktree at `<workspace>/<repo>/<branch-name>/`, the sibling of the main checkout inside the repo folder. If a project's main checkout is still flat — the project folder is itself the checkout, as with a single-repo project — restructure it before creating any worktree: move the checkout into `<repo>/<base-branch>/` (e.g. `my-app/main/`), run `git worktree repair` from it, and bring any existing worktrees inside with `git worktree move`; check first that no dev server is running from the old path. Keep every file of a project inside its own folder: documents, mockups and sketches go in that project's `docs/` folder (`<workspace>/docs/` for a multi-repo workspace, `<repo>/docs/` for a single-repo project), never in a folder shared with other projects or at the workspace root. Create one worktree per work branch, and never switch the main checkout to a work branch for task work. If a worktree for the branch already exists, reuse it. Run installs, builds, tests and servers from inside the worktree.
- Switch to main worktree: when told to "switch this to the main worktree" (or equivalent), it means removing the linked worktree directory and checking out the branch directly in the main repository checkout already on the machine, not keeping a separate linked worktree. Confirm both the linked worktree and the main checkout are clean before removing the linked worktree (`git worktree remove`) and switching the main checkout's branch.
- Merged means real commits: when closing, removing, or cleaning up worktrees or branches because they are "merged", a branch counts as merged only if it has at least one commit of its own (`git rev-list --count <base>..<branch>` is non-zero before the merge, or `git cherry` shows its patches upstream) **and** those commits are in the base, or it has a merged PR. A branch whose tip is merely an ancestor of the base with zero commits of its own is a freshly created, unstarted branch - treat it as active work, never as merged. Before removing any worktree, report each one's own-commit count and PR state, and skip zero-commit branches unless the user explicitly names them.
- Post-merge worktree cleanup: after merging a PR whose branch is checked out in a linked worktree, automatically remove that worktree (`git worktree remove`) and delete its local branch straight away, without asking — this is standard cleanup, not a pending delete. First confirm the PR is merged, the worktree is clean, and the branch has real commits of its own (see Merged means real commits); if any check fails, skip the cleanup and report why. Delete the branch with `git branch -d`, falling back to `-D` only because the PR is confirmed merged (squash merges defeat `-d`). Never touch the main checkout, any other worktree, or the remote branch. Report the removed worktree and branch in Results.
- Fork PRs: when a repo is a fork with both fork and upstream remotes for the same base branch, open the fork-base PR right away when the work is done, and open the upstream-base PR only after asking and receiving explicit approval. Publish the work branch to whichever remote each PR requires before opening it, and clearly report the PR links.
- Pull request base enforcement: before opening a pull request, verify that its destination is the repository's recorded long-lived base branch, such as `main`, `master`, or `development`. For a normal repository, open the PR against the base branch on `origin`. For a forked repository, open the fork PR against the base branch on `origin` right away; open the upstream PR against the corresponding base branch on `upstream` only after asking and receiving explicit approval. Never open a PR against a feature, task, or dependency branch.
- Commit and push after AI work: after every completed AI task that changes files in a Git repository, run the required validation, commit the completed changes, and push the branch to its configured remote. If changed files are in a Git repository but no remote is configured, the work is intentionally local/private, or the user explicitly requested no commit/push, state that commit/push was skipped and why. Do not mention commit/push for tasks that do not change files in a Git repository unless it is relevant or the user asks.
- Fast-ship workflow: shipping speed is the priority. Work runs in two phases. *Decide*: the plan, open questions, and the issue/branch are agreed up front. *Ship*: once the user gives the go-ahead, carry the work through development, local review, PR, merge, deployment and test-readiness without stopping to ask. Stop only for a real blocker, a destructive or irreversible action outside this flow, or a PR against a fork's `upstream`. Report once at the end.
- Quickest sound path: during development, choose the path that is both best and quickest, and decide it yourself without asking. Take a slower or harder path only when it is truly necessary — correctness, security, data safety, or the acceptance criteria cannot be met otherwise — and say why in Results.
- Pull requests and merges: after implementation, run compatible automated checks first, run curl/API testing only when the user asks for it, then open one PR for the task plus the approved upstream PR where the fork PR rule applies. Set each pull request title to exactly match its source branch name, preserving the full issue number, prefixes, and hyphenated slug. Open pull requests as ready for review by default; use a draft pull request only when the user explicitly requests one or the work is knowingly incomplete. Merge a PR against `origin` without asking once the automated checks pass and the implementing agent has completed its local review and fixed its findings (see Fast-ship workflow and Deployment path). A PR against a fork's `upstream` is never opened or merged without explicit approval.
- Review findings table: always report PR review findings (bot reviews, local reviews, reviewer comments) as a table with the columns **Priority**, **PR**, and **Description**, sorted highest priority first. The PR column shows the linked PR number (e.g. `#123`); each description is one clear sentence saying what is wrong and where (`file:line`). If there are no findings, say so in one line. Report the table in the final summary, after the merge — never as a stop before merging.
- PR status table: whenever the user asks for PR status, and in Results whenever several PRs are involved, report the PRs in one table with these columns: **PR** (the linked PR number); **Repo · Issue**; **About** (a few words); **State** (Open, Mergeable, Conflict, Merged or Building); **Reviews** (bot review ✓, pending, or N open, plus the implementing agent’s local review result); **Next** (the next step or blocker). Read each state live from GitHub (`gh pr view`), never from memory. List PRs that need the user's action first. A merged PR appears in one report after it merges, then drops off. Keep the table within the table-width rule, with short cells.
- PR timing vs. user review: open the PR as soon as the applicable automated checks (and curl/API testing, when the user asked for it) pass — do not wait for the user to finish their own manual review of the changes first. The user's review can happen on the open PR itself, in parallel with any further work.
- Assistant guide update with every feature PR: when a project has an in-app AI assistant that answers from a guide shipped with the code, update the matching guide page whenever a PR adds or changes user-facing behaviour, as part of the same task. If the guide lives in the same repo, do it in the same PR; otherwise open a companion guide PR in the guide's repo, branched from its base and cross-linked with the feature PR. Add index entries for new pages and keep any route list the guide uses current. If a change has no user-facing effect, write `No guide change needed` in the PR body. Report the guide PR alongside the feature PR.
- Translations with every PR: like the assistant guide update, every PR that adds or changes user-facing text must include that text in every locale the app supports, in the same PR (e.g. each folder under the app's locales directory). Translate it yourself unless the project has a confirmed automatic translation service. Never leave a new key only in the default language. In the PR body, list the locales updated, or write `No copy change`.
- PR bot review: after opening any PR, handle reviews per the Codex review escalation rule: the implementing agent’s local review gates the merge, and the GitHub bot review runs asynchronously.
- Merge ready PRs without waiting for siblings: merge each PR against `origin` as soon as its automated checks pass, the implementing agent’s local review is complete and its findings are fixed, and its dependencies are merged. Merge providers before consumers and ship companion documentation with or after its feature. Let independent PRs proceed as they become ready, subject to the deployment rules. A PR against a fork's `upstream` requires explicit approval to open or merge.
- Codex review escalation: the agent implementing the change runs its own local gating review when the PR opens or is updated. In Claude Code, run `/code-review`. In Codex, use local Codex review, such as `codex review --base <base>` from the PR branch with the current target ref as `<base>`. Fix local findings and push the fixes before merging. The Codex bot review may still be requested when the PR opens (comment `@codex review` if `chatgpt-codex-connector[bot]` does not start on its own), but never wait for it and never hold a merge for it. If a GitHub bot review arrives later, including after the merge, check each finding against the current code: reply `Fixed in <sha>` on the thread of any finding already fixed and resolve it, then collect the still-valid findings into one follow-up issue, created without asking, rather than blocking or reopening the shipped work. If the bot posts its usage-limit notice ("You have reached your Codex usage limits for code reviews"), carry on without it. Report the local review findings, and any Codex follow-up issue, in the final summary.
- Review finding triage: batch valid fixes from local review and reviewer comments that fit the agreed behavior, including business-logic fixes supported by the acceptance criteria or established requirements. Ask the user only when a decision about intended behavior is necessary to ship safely or meet the acceptance criteria. Track other valid findings outside the agreed scope as follow-up work. Handle Codex bot findings under the Codex review escalation rule and summarize outcomes at the end.
- Later-features option: every decision question that offers to fix, build or change something starts with **Today:**, stating in one line what the system does right now, and its options always include a **keep as is** option and an option to record it as a later feature, alongside the fix-now option(s) such as "fix now" or "follow-up", instead of offering only "fix" vs "out of scope". When I pick the later-feature option, record the item in both places: under a **Later features** section in the description of the closest related Linear issue (or the GitHub issue, for non-Linear projects), and in the **Later features** tab or section of the project's flow/design document, if the project has one. Write each entry as a bold one-line title naming the issue, then **Today:** what happens now, then **Wanted:** the future behaviour to achieve; one entry per item, and never an acceptance criterion. Entries recorded before this change stay as they are.
- Post-merge action polling: after merging a pull request that triggers CI/deploy workflows, poll the relevant workflow every 15 seconds until it completes. Do not report deployment success before completion. If it fails, inspect the failing job and logs, report the confirmed error, and when the failure is at build, deploy over SSH per the Deployment path rule.
- Deployment path: deploy by merging the PR on GitHub so the Actions workflow deploys. Before merging, check whether another deployment is already running (for example from another session, via `gh run list`) and wait for it to finish. If the Actions deployment fails at build, deploy over SSH automatically and report it. Follow the project's local deployment rules wherever they exist. A deployment must end up through, never left failed.
- Test-ready after merge: after merge and deployment, if seeing the change needs a local step (for example a mobile app), bring the merged changes into a viewable state — update the main checkout to the merged base when it is clean, build what is needed — and report how to view it. If the main checkout has WIP, leave it and report.
- No rollback images: never create rollback images, backup tags, or copies of containers or images (e.g. `docker tag … :rollback-*`) before or during a deploy unless the user explicitly ask for one. If a deploy breaks, recover by deploying again: fix forward, or redeploy the previous known-good commit. Do not keep backup artefacts around or ask the user about deleting them later.
- TypeScript: after TypeScript changes, run `tsc --noEmit` on the affected package or packages before staging or committing.
- Backend/API/proxy validation: when working on backend, API, endpoint, or proxy behavior, first run compatible automated checks for the affected code path and any database-compatible validation available. Automated checks are always mandatory. curl/API testing is no longer run by default — run it only when the user asks for it; without it the order is automated checks first, PR second. When curl/API testing is asked for, the order is automated checks first, explicitly confirm the relevant backend/service is running and responding second, curl/API testing third, execution-log verification fourth, PR fifth. When curl/API testing has been asked for and the backend/service is reachable, run curl/API tests for the changed or affected path. After curl/API or execution testing, inspect relevant time- or trace-matched service logs when available and confirm the matching operation, status/result, and absence of relevant errors or exceptions; an HTTP response alone is not sufficient proof that execution completed correctly. If requested curl/API or log verification is not run, state the concrete blocker. Do not silently skip requested backend availability checks, curl/API tests, or available execution-log verification.
- Next.js validation: for Next.js fixes, run `tsc --noEmit` and lightweight checks such as `git diff --check` by default. Do not run production builds unless explicitly requested.
- Server start/restart: starting or restarting local servers is allowed when needed to run or verify work. Before starting a service, first consider whether it needs to be built or rebuilt and do that build step first. Never stop or restart the user's running server; start my own instance on a free port (see Own test port for curl), and restart only instances I started. Clean up any temporary exposure such as ports or tunnels afterward.
- Own test port for curl: curl/API testing runs only when the user asks for it (see Backend/API/proxy validation); when it runs, always run curl/API tests against my own instance of the app, never the user's main dev server. Start it on the base port + 50 (e.g. 4000 → 4050); if that port is taken, use the next free port up to base + 99, checked with `ss -ltn`. It uses the same database and env as the user's dev server. Never stop, restart, or take over the user's running server or its port. Stop my instance when testing ends, and show the port used in the curl results table.
- Development-mode restart reporting: before finishing development work, confirm how the affected app runs in development and whether hot reload or watch mode applies the changes automatically. When hot reload or watch mode applied the change, do not show a restart or rebuild warning. When only a restart is required, end the final summary with **APP NEEDS RESTART TO APPLY - restart it.** When build artifacts must be regenerated, end the final summary with **APP NEEDS REBUILD TO APPLY - rebuild and restart it.** For workspace maintenance, intentionally stopped services, or work that does not require an application to apply changes, report the status normally without either warning.

## Security

- Temporary exposure cleanup: when opening or starting any service, port, tunnel, firewall rule, public listener, share, or other network exposure for a task, close/stop/restrict it after finishing unless the user explicitly asks to leave it open.

- Deferred deletes: during a task, never run a command that triggers the dangerous-delete permission prompt (even in bypass-permissions mode) — e.g. `rm`/`rm -rf` on project or user files, `git worktree remove`, `git branch -d`/`-D`, `git push --delete`, or deleting remote resources — because it stalls the task. Finish the task first; then, at the end, list every pending delete (what, where, why) under Considerations, ask for approval, and run the deletes only after the user approves. Throwaway files in your own scratchpad or temp directories that do not trigger the prompt are exempt. Exception: post-merge worktree and local-branch cleanup under the Post-merge worktree cleanup rule runs automatically and is not deferred.

- MongoDB Atlas IP rejection: when a MongoDB connection fails because the client IP is not allowed (Atlas `IP address ... is not whitelisted`, or a connection timeout against an Atlas cluster), first confirm the machine's current public IP, then resolve it by adding that IP as a specific `/32` entry in the cluster project's Atlas Network Access allowlist. Never add an all-addresses range (a `/0` covering every IP) or any other broad range. Report which IP was added and to which Atlas project. A `/32` entry for the user's own development machine may stay; an entry added for any other host, CI runner, or temporary environment must be removed after the task under the temporary exposure cleanup rule.

- Never rsync `-a` to a remote home directory: when copying files to a remote host with rsync, never use `-a`/`--archive` — it expands to `-rlptgoD`, and the `-o`/`-g`/`-p` inside it push the local uid/gid/mode onto the remote. Use `-rlt` instead (recurse, symlinks, times). Always target the leaf directory, never the home directory itself: with a trailing slash on the source, rsync also applies the source directory's own owner and mode to the destination directory, turning a `700` root-owned home into a group-writable one owned by the local uid. The remote SSH daemon with `StrictModes yes` then refuses to read `authorized_keys` from a group-writable or non-owned home, silently ignores the key, and falls back to asking for a password — locking key auth out of every host the sync touched. Never resolve this by disabling `StrictModes`; that removes a wanted protection. Repair a damaged host by restoring the home directory to `700` and root ownership, then re-verify. Plain file copy over SSH cannot cause this — it never sets ownership, even when preserving times.

- Verify SSH access after every fleet sync: immediately after pushing files to a remote host, confirm the destination home directory is still `700` and owned by the target user, then prove key auth still works over a fresh, batch-mode connection before moving on to the next host. Do both checks while a working connection or a known-good fallback credential still exists, so any breakage can be repaired on the spot — never finish a sync session leaving a host that might reject key auth on the next login. Prefer a tar-pipe over SSH, which does not alter the destination home directory; if rsync is used, it must follow the `-rlt`/leaf-directory rule above. - Negation and polarity check: users frequently drop or misplace negations — "do" where they mean "don't", and the reverse. Never silently invert an instruction. When an instruction's polarity is ambiguous and the surrounding context suggests the opposite of the literal words, resolve it by consequence, not by guess: for read-only or trivially reversible actions, take the safer non-acting reading, state the assumption in one line, and continue; for anything destructive, irreversible, or outward-facing — deleting, overwriting, force-pushing, merging, deploying, publishing, sending, or changing remote server state — stop and ask in plain text before acting.
